# 反模式与高频问题（FAQ）

按症状查找。包括既往现场问题与 v1.4.0 的五级候选策略；未通过本机实测的客户端能力会明确报告。

## 派发与可见性

**Q：调度器显示任务已派发，但桌面里找不到会话？**
先看 `status` 里该包的 `visibility.confirmed`。可见性需要三要素齐备：正确项目 + 选中目标 session + 正文出现 `协作任务包：包ID`。缺任一都算未确认。修复方式：在实际任务项目根目录执行 `node <runner> open <包ID>`——它只重新定位已有会话，**不重发消息、不重建会话**。显示失败 ≠ 重新派发：任务可能已在运行，重派会造成双会话。旧 smoke 会话被选中不算数。

**Q：能不能把任务派给主持方自己（engine = coordinator）？**
不能，调度器直接拒绝。主持方就是写 Spec/验收的聊天，Exec 必须是其他工具的桌面会话；单工具能完成的任务不需要本 skill。`auto` 按候选顺序选择其他工具；旧 `both` 只指 ZCode 与 WorkBuddy 国际版。

**Q：两个包要写同一个文件，能并行吗？**
不能。归属交叠的包由调度器自动串行（`canStart` 文件重叠检查，含大小写与目录层级）。真正会互相冲突的还有：共享构建输出、依赖安装、端口、数据库、Git index——计划者必须把这些分配唯一写入责任或改为依赖串行。文件归属是协作约定，不是操作系统沙箱。

## 状态与验收

**Q：执行器说"完成了"，能直接算通过吗？**
不能。执行结束只是 `exec_done`（交回），必须主持方逐项核对真实产物、diff、测试退出码后执行 `verify` 才是 `verified`。不得把执行者自测称为验收通过。

**Q：verify 报退出码 2，"存在归属清单外变更"？**
运行前后有文件指纹比对，任何归属清单外的增/改/删都会阻断验收——**包括主持方/用户自己迟写入的文件**（比如调度器启动后才把笔记放进项目根目录）。处理：查明每个变更的来源；确认无害后，把用户侧材料移入 `.work-together/`（不参与指纹）或删除。这是事后检测，不是写入拦截，也不会自动回退。

**Q：包状态变成 unknown / failed 怎么办？**
unknown = 执行结果未知（如连接断开）。禁止重派：先到原桌面会话查最终状态；有 sessionId 时用 `run plan.json --resume` 恢复（复用原会话 ID）。failed 时先辨别是否为额度/不可用且原会话已经停止；只有确认停止后才允许按候选序列转交下一项。普通产物修正仍**退回原会话修复**——向同一 sessionId 发修正指令，必须用**新的请求 ID**（复用旧 ID 会被缓存吞掉）；修好后产物重新逐字节验收。

**Q：取消一个包会发生什么？**
`cancel <包ID>` 把停止请求送到原会话并写 controls 记录；必须确认桌面最终状态后再释放该包的文件归属。调度器不删除原会话、不做 git reset、不清理用户修改。

## 环境与启动

**Q：能在 macOS 上用吗？**
macOS 是**实验性适配、未现场验证**：核心调度逻辑与页面匹配已平台化并有跨平台单测，darwin 启动器（`start-desktops.sh`）只做过语法校验。Mac 上首次使用前必读 [macos.md](macos.md) 并逐项执行验证清单；`doctor` 连不上会明确失败——那是唯一诚实的入口，通过验证清单前不要在正式任务里使用 macOS 路径。

**Q：doctor 失败 / 调试端口不可用？**
先查活跃会话，再跑 `start-desktops.ps1 -Engine <具体engine>`；`auto` / `all` 会准备全部五款：健康实例直接复用；未开调试端口的运行实例会被自动退出并重启（托盘进程超时后强杀同安装路径进程）。当前项目有运行中任务时默认保护现场，明确要中断加 `-ForceRestart`。端口仅本机（ZCode=19331、Qoder 国际/国内=19333/19334、WorkBuddy 国际/国内=19332/19335），不要转发外网。桌面桥绑定已验证版本（ZCode 3.15.3 / WorkBuddy 5.7.6）；应用升级后必须重跑 doctor；接口不兼容时明确失败，先修适配。doctor 通过只证明本次桥与模型元数据预检，不证明模型请求成功。

**Q：headless 主持（codex exec / WorkBuddy 命令沙箱）里启动调度器总失败？**
这些沙箱不承载长驻进程：codex exec 回收分离子进程；WorkBuddy 在策略层拦截 WMI/Start-Process。分工应是：**调用方（用户或交互式宿主会话）启动调度器，主持会话只做 Spec/Plan/监控/验收**。注意 WorkBuddy 沙箱的后台任务机制能另起调度器，但会与已有实例撞 `runner.lock`（单调度器约束，属预期）。本机经 MSYS 调用时 `Start-Process -WindowStyle Hidden` 会以退出码 127 静默失败，分离启动用 WMI `Win32_Process.Create` 或宿主后台进程。

**Q：同目录能同时跑两个调度器吗？**
不能。`runner.lock` 保证单实例；意外退出会残留锁，`--resume` 会先确认旧进程已退出再复用会话。

## 计划与模型

**Q：跑到一半需求变了，直接改 plan.json 行吗？**
不行。恢复时校验 planHash，计划变化会被拒绝——禁止静默更换文件归属或依赖。正确做法：等本轮收尾（或 cancel），归档 `.work-together` 后按新计划开新一轮。

**Q：怎么选模型？**
默认 `engine=auto`：ZCode 精确 `GLM-5.3-FlashX` → Qoder 国际版免费 DeepSeek → Qoder 国内版免费 DeepSeek → WorkBuddy 国际版免费 DeepSeek → WorkBuddy 国内版免费工具模型。`workbuddy` 是国际版别名。后四项只接受当前模型目录明确零费率，Auto 和空费率不代表免费；无免费项时跳到下一候选，禁止收费回退。显式 engine 从该项往后选择，`fallback=false` 才锁定单项。

**Q：限时免费结束、额度用尽或助手不可用，能自动换吗？**
用户已授权按五级顺序切换。预检失败可直接尝试后项；任务已发出则必须确认旧会话已停止，带已有产物和原会话信息接续。超时、连接断开、创建/发送结果不明均不能推断停止；保持 `unknown` 并查原会话。每任务每候选至多尝试一次，耗尽后报告具体原因。

**Q：国内与国际版能共用一个端口或安装路径吗？**
不能。各地区客户端独立指定路径和端口，避免连错账号/模型目录。启动器只操作所选 exe 的进程；`-WorkBuddyPath` 仅覆盖国际版。已有健康客户端直接复用，预检另一地区版本无需重启它。当前项目保护不能替代其他项目活跃会话检查。

**Q：助手可以替我补网页或小程序截图吗？**
可以把截图作为归属明确的任务包交给具备对应工具的助手，列出页面、步骤、输出文件与文稿回填位置。截图是否成功必须检查真实图像及最终文稿渲染；受登录、设备或工具能力限制时报告缺口，不伪造界面。

**Q：执行器能写共享记忆/工作日志吗？**
不能。执行器禁止写 `.workbuddy-ai/memory`、`MEMORY.md` 等共享文件（越界写入会被指纹检测抓到并阻断验收）；需要记忆时在最终回复里交给主持方统一整理。

## 外部驱动

**Q：用脚本驱动 `Desktop.create` 时报 "cwd lost its path separators"？**
cwd 被多层字符串转义吃掉了路径分隔符。从外部传路径应走 argv/env 等免转义通道；注意 `node -e` 模式下附加参数从 `process.argv[1]` 开始。
