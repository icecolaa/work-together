---
name: work-together
description: 让 Codex 规划并验证，由用户指定的 ZCode 或 WorkBuddy 桌面会话在同一工作目录并行执行独立任务包，跟踪待办、人工介入和验收证据。
---

你负责 Spec、Plan 和独立 Verify；所选外部桌面执行器负责 Exec。任务开始时读取用户的 `executor=zcode|workbuddy`，未指定时询问，不擅自切换。简单任务优先单包；仅文件归属和依赖允许时并行。

1. 先读现场、AGENTS.md、现有修改。将目标、输入、禁止修改边界、交付物、逐条验收条件和回退入口写入 `SPEC.md`。不覆盖用户已有 Spec。
2. 写 `PLAN.md` 及 `plan.json`：每包有唯一 id、prompt、files、acceptance、dependsOn；默认 concurrency=2。执行器针对整轮选择。依赖包必须经 Codex 验收才可启动。目录归属覆盖子目录，交叠包由调度器串行；共享构建输出、依赖安装、Git index、锁文件也要分配唯一写入责任。
3. 读 [运行说明](references/operations.md)，使用本 skill 的脚本连接**真实桌面会话**。先 doctor；桌面登录不代表 API 或 CLI 已登录。接口不可用时报告缺口，不伪造会话、不直接写桌面数据库、不自动替换其他执行器。首次本地调试适配需说明它是版本相关的私有桌面桥。
4. 用隐藏后台进程运行 `workflow.mjs run <plan.json>`，工作目录为项目根；stdout/stderr 重定向到 `.work-together` 或用户指定本地日志路径。工具会话返回的后台进程不等于永久驻留服务。主聊天仅报告状态变化、交付结果和人工决策；详细快照在本地 JSONL，不粘贴大段日志。
5. 使用当前 Codex 环境真实提供的计划工具（若有）同步任务；没有则维护 PLAN.md 的勾选项。定期读紧凑 status/watch，主会话在本轮保持跟进，独立工作完成后再收尾。skill 本身不能在 Codex 回合结束后主动唤醒聊天：只有配置了可用的宿主通知机制才能承诺跨回合自动汇报。
6. 状态包括 queued、running、needs_user、exec_done、verified、failed、unknown、blocked、cancelled。needs_user 时给出简短回顾卡：完成了什么、卡在哪里、具体需回答什么、会话 ID、下一步。通过执行器原生待办维护本包进度，不把 Codex 的总计划假称为外部工具原生全局计划。后台其他无依赖包可继续。
7. 需新增决策的权限/问题由用户去对应桌面会话回应；已有明确授权、且操作与 Spec 范围完全相符时可经原生接口逐项批准一次，不扩大为永久允许，不改成绕过权限模式。失联/超时先查原会话，unknown 不重派；取消后确认停止再释放文件归属。恢复复用持久会话 ID。
8. Exec 结束仅记 exec_done。你逐项读取真实产物、检查 diff、独立运行适合改动的测试，必要时看截图/控制台/应用后台状态，证据映射到 Spec 条件。失败退回原会话修复。将独立验收记录交给 `verify` 命令；不能仅凭执行者“通过”结案。所有包 verified 后交付，更新 PLAN.md 并给出简洁总报告。

文件归属是协作约定，非操作系统隔离：真正相互冲突的构建/依赖/可变外部状态必须串行，或经用户接受后使用 worktree。不要承诺“同目录完全互不干扰”。发布、推送、发消息按当前用户授权范围处理。日志、截图、桌面会话、账号配置和密钥默认只留本地。
